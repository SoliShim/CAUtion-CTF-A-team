1. Command Injection

문제 목표DNS 조회 기능을 이용해 서버의 /flag 파일을 읽습니다.
핵심 취약점사용자가 입력한 host 값이 shell 명령어 문자열에 그대로 붙고, os.popen()으로 실행됩니다.
취약 코드cmd = f"nslookup {host}"
최종 페이로드example.com;sort /fla?

풀이 사고 흐름

처음에는 정상 기능부터 확인합니다. 입력칸에 example.com을 넣으면 DNS 조회 결과가 나옵니다. 즉 서버가 내부에서 nslookup 같은 명령어를 실행한다는 것을 알 수 있습니다.

그다음 의심할 지점은 host 입력값입니다. 사용자가 넣은 문자열이 명령어 뒤에 붙는다면, shell 문법을 같이 넣었을 때 새 명령이 실행될 수 있습니다.

세미콜론을 떠올립니다. Linux shell에서 명령1;명령2는 두 명령을 순서대로 실행합니다. 그래서 host 자리에 example.com;id 같은 형태를 넣는 발상을 할 수 있습니다.

하지만 쉬운 명령은 필터에 막힙니다. cat, flag, grep, bash 같은 단어가 차단됩니다. 이때 "파일을 읽는 다른 명령은 없을까?"와 "flag라는 단어를 직접 쓰지 않는 방법은 없을까?"로 생각을 바꿉니다.

sort와 glob을 조합합니다. sort 파일명도 파일 내용을 출력할 수 있고, /fla?는 shell에서 /flag와 매칭됩니다. 따라서 금지어를 직접 쓰지 않고도 같은 파일을 읽을 수 있습니다.

개념 이해

Command Injection은 입력값이 운영체제 명령어 일부로 실행될 때 생깁니다. 이 문제에서는 서버가 nslookup 사용자의입력을 shell에 넘깁니다. shell은 세미콜론 ; 뒤를 새 명령으로 해석하므로, DNS 조회 뒤에 파일 읽기 명령을 이어 붙일 수 있습니다.

문제의 필터는 강해 보이지만 완전하지 않습니다. flag라는 단어는 막지만 /fla? 같은 shell glob은 막지 않고, cat은 막지만 sort는 막지 않습니다.

Step by Step

  1. 정상 입력 example.com으로 DNS 조회 페이지가 동작하는지 확인합니다.
  2. 소스에서 os.popen()과 cmd = f"nslookup {host}"를 확인하고, 입력값이 shell 명령어에 직접 붙는다고 판단합니다.
  3. 금지어 목록을 보고 cat /flag는 막힌다는 것을 확인합니다.
  4. 파일 내용을 출력할 수 있는 허용 명령 sort를 선택합니다.
  5. flag 단어를 직접 쓰지 않기 위해 /fla?를 사용합니다.
  6. 입력칸에 아래 값을 넣습니다.
example.com;sort /fla?
  1. DNS 조회 결과 아래쪽에 flag가 함께 출력됩니다.
최종 정답: FLAG{qu0te_spl1tt1ng_byp4ss_k3yw0rd_f1lt3r!}

왜 이렇게 하는가?

필터는 특정 단어만 막습니다. 하지만 shell에는 같은 결과를 내는 표현이 많습니다. 이 문제의 핵심은 차단 목록과 shell 문법 사이의 빈틈을 찾아 cat /flag와 같은 효과를 다른 표현으로 만드는 것입니다.

2. SQL Injection

문제 목표숨겨진 SQLite 테이블을 찾아 flag 값을 조회합니다.
핵심 취약점사용자 입력이 파라미터 바인딩 없이 SQL 문자열에 직접 들어갑니다.
취약 코드SELECT username, dummy_pw FROM accounts WHERE username='{user_input}'
최종 페이로드'\tUNION\tSELECT\ttop_secret,flag_val\tFROM\tsecret_vault_8f2a\tWHERE\t'1'='1

풀이 사고 흐름

처음에는 작은따옴표를 의심합니다. 로그인 또는 계정 조회 문제에서 입력값이 SQL에 들어간다면 '로 문자열을 닫을 수 있는지 확인합니다.

공백이 막히면 우회 공백을 찾습니다. 필터는 일반 공백 , --, /*만 막습니다. SQLite는 탭 문자도 공백처럼 처리하므로 \t를 사용합니다.

먼저 전체 계정 조회로 취약점을 확인합니다. ' OR '1'='1 형태를 탭으로 바꾸면 모든 계정 행이 출력됩니다. 여기서 SQL Injection이 된다는 것을 확인합니다.

그다음 DB 구조를 봅니다. flag가 현재 화면에 없다면 숨겨진 테이블을 찾아야 합니다. SQLite에서는 sqlite_master에 테이블 이름과 생성 SQL이 들어 있습니다.

테이블과 컬럼을 알면 최종 조회를 합니다. secret_vault_8f2a 테이블의 top_secret, flag_val 컬럼을 UNION SELECT로 화면에 출력합니다.

개념 이해

SQL Injection은 입력값이 데이터가 아니라 SQL 문법으로 해석될 때 발생합니다. 이 문제는 username='입력값'처럼 작은따옴표 안에 입력을 넣으므로, 입력값이 '로 시작하면 원래 문자열을 닫고 뒤에 SQL 문법을 추가할 수 있습니다.

서버가 마지막 작은따옴표를 자동으로 붙이기 때문에, 페이로드 끝도 문법적으로 맞춰야 합니다. 주석이 막혀 있으므로 마지막에 WHERE '1'='1 같은 조건을 붙여 quote balance를 맞춥니다.

취약점 확인

공백 대신 Tab을 넣어 아래 값을 입력합니다.

'	OR	'1'='1

실제 SQL은 대략 아래처럼 됩니다.

SELECT username, dummy_pw FROM accounts WHERE username='' OR '1'='1'

결과에 guest, admin 행이 보이면 입력이 SQL 문법으로 실행된 것입니다.

테이블 구조 확인

'	UNION	SELECT	name,sql	FROM	sqlite_master	WHERE	type='table

여기서 숨겨진 테이블 secret_vault_8f2a와 컬럼 top_secret, flag_val을 확인합니다.

Step by Step

  1. 입력칸에 '를 넣어 SQL 문법 오류가 나는지 확인합니다.
  2. ' OR '1'='1로 전체 계정 행이 나오는지 확인합니다.
  3. sqlite_master를 UNION SELECT로 조회해 숨겨진 테이블 이름을 찾습니다.
  4. 찾은 테이블과 컬럼 이름으로 아래 최종 페이로드를 넣습니다.
'	UNION	SELECT	top_secret,flag_val	FROM	secret_vault_8f2a	WHERE	'1'='1
  1. 결과 테이블에 TOP_SECRET / FLAG...가 출력됩니다.
최종 정답: FLAG{m4st3r_0f_sq1_4nd_d3vt00ls}

왜 이렇게 하는가?

이 문제는 로그인 우회보다 데이터 추출이 목표입니다. 화면에 두 개의 컬럼이 출력되므로, UNION SELECT도 컬럼 두 개를 맞춰서 넣으면 숨겨진 테이블의 값을 기존 결과 화면에 끼워 넣을 수 있습니다.

3. SSTI

문제 목표프로필 자기소개 입력을 이용해 서버의 /app/flag.txt를 읽습니다.
핵심 취약점사용자 입력이 Jinja 템플릿 문자열 안에 들어간 뒤 render_template_string()으로 다시 렌더링됩니다.
취약 코드{p['bio']}가 들어간 문자열을 render_template_string(profile_template)으로 실행
최종 페이로드{{url_for|attr('_'*2+'globals'+'_'*2)|attr('_'*2+'getitem'+'_'*2)('_'*2+'builtins'+'_'*2)|attr('_'*2+'getitem'+'_'*2)('_'*2+'import'+'_'*2)('os')|attr('popen')('cat /app/flag?txt')|attr('read')()}}

풀이 사고 흐름

처음에는 템플릿 계산식을 넣어 봅니다. 자기소개 칸에 {{7*7}}을 넣었을 때 49가 나오면, 서버가 입력을 단순 텍스트가 아니라 템플릿 코드로 실행한다는 뜻입니다.

그다음 목표는 파일 읽기입니다. README에 flag.txt 파일을 읽으면 됩니다라고 되어 있으므로, Jinja에서 Python 객체를 타고 들어가 명령 실행 또는 파일 읽기까지 도달해야 합니다.

필터 때문에 정석 페이로드는 막힙니다. 원격 서버는 ., __, class, mro, subclasses, request, self, config 같은 패턴을 막습니다.

점 접근은 attr로 바꿉니다. a.b처럼 쓰면 점이 필터에 걸리므로 a|attr('b') 형태를 사용합니다.

더블 언더스코어는 문자열 조합으로 만듭니다. __globals__를 직접 쓰면 막히지만 '_'*2+'globals'+'_'*2는 렌더링 시점에 같은 문자열이 됩니다.

개념 이해

SSTI는 Server-Side Template Injection입니다. Jinja 템플릿에서 {{ ... }} 안의 표현식은 서버에서 계산됩니다. 문제는 사용자의 자기소개가 템플릿 문자열 안에 그대로 삽입되고, 그 전체 문자열이 다시 렌더링된다는 점입니다.

Flask 템플릿에는 url_for 같은 함수가 기본으로 들어 있습니다. 함수 객체의 전역 변수 목록을 따라가면 Python의 __builtins__에 접근할 수 있고, 거기서 __import__('os')를 통해 명령 실행에 도달할 수 있습니다.

취약점 확인

자기소개 칸에 아래 값을 넣습니다.

{{7*7}}

결과가 49이면 SSTI가 맞습니다.

Step by Step

  1. /create 페이지에서 새 프로필을 만듭니다.
  2. 자기소개에 {{7*7}}을 넣어 계산되는지 확인합니다.
  3. 필터가 .과 __를 막으므로, 점 접근 대신 attr 필터를 사용합니다.
  4. __globals__, __getitem__, __builtins__, __import__는 직접 쓰지 않고 문자열 조합으로 만듭니다.
  5. flag.txt의 점도 필터에 걸리므로 shell glob인 flag?txt로 바꿉니다.
  6. 자기소개 칸에 아래 최종 페이로드를 넣습니다.
{{url_for|attr('_'*2+'globals'+'_'*2)|attr('_'*2+'getitem'+'_'*2)('_'*2+'builtins'+'_'*2)|attr('_'*2+'getitem'+'_'*2)('_'*2+'import'+'_'*2)('os')|attr('popen')('cat /app/flag?txt')|attr('read')()}}
  1. 생성된 프로필 카드의 자기소개 영역에 flag가 출력됩니다.
최종 정답: FLAG{n0_d0t_n0_und3rsc0r3_n0_pr0bl3m}

왜 이렇게 하는가?

이 문제의 핵심은 "필터가 막는 문자열을 입력에 직접 쓰지 않는다"입니다. Jinja가 표현식을 계산하는 시점에 금지 문자열이 만들어지도록 하면, 입력 필터를 지나간 뒤 원하는 객체 접근을 할 수 있습니다.

4. IDOR

문제 목표숨겨진 내부 공유 노트를 찾아 flag가 들어 있는 내용을 읽습니다.
핵심 취약점공유 노트 조회와 존재 확인 API가 로그인 여부만 확인하고, 현재 사용자의 접근 권한은 확인하지 않습니다.
취약 코드SELECT * FROM share_notes WHERE note_key=?
최종 키internal_backup → aW50ZXJuYWxfYmFja3Vw

풀이 사고 흐름

처음에는 guest로 로그인합니다. 로그인 페이지에 guest / guest123 계정이 제공됩니다. 문제는 인증 우회가 아니라 로그인 후의 객체 접근 문제라고 볼 수 있습니다.

예시 공유 링크를 관찰합니다. challenge 페이지에 /share/Z3Vlc3Rfbm90ZQ==가 보입니다. 끝의 == 모양 때문에 Base64를 의심할 수 있습니다.

디코딩하면 의미 있는 이름이 나옵니다. Z3Vlc3Rfbm90ZQ==를 디코딩하면 guest_note입니다. 즉 공유 키는 랜덤 토큰이 아니라 예측 가능한 이름을 인코딩한 값입니다.

존재 확인 API를 oracle로 씁니다. /api/share/check?key=VALUE는 존재하면 200, 없으면 404를 돌려줍니다. 이 차이로 숨겨진 note_key 후보를 테스트할 수 있습니다.

힌트에 맞춰 내부 백업 이름을 추측합니다. 내부 공유 객체라면 internal_backup 같은 이름이 자연스럽습니다. 이를 Base64로 바꾸어 확인합니다.

개념 이해

IDOR는 Insecure Direct Object Reference입니다. URL이나 파라미터에 들어가는 객체 ID를 사용자가 바꿀 수 있는데, 서버가 그 객체를 볼 권한이 있는지 확인하지 않으면 발생합니다.

Base64는 암호화가 아니라 인코딩입니다. 누구나 원래 문자열로 되돌릴 수 있으므로 접근 제어 수단이 될 수 없습니다.

Step by Step

  1. /login에서 guest / guest123으로 로그인합니다.
  2. challenge 페이지의 예시 링크 /share/Z3Vlc3Rfbm90ZQ==를 확인합니다.
  3. 터미널에서 예시 키를 디코딩합니다.
echo 'Z3Vlc3Rfbm90ZQ==' | base64 -d
# guest_note
  1. 숨겨진 객체 이름으로 internal_backup을 추측하고 Base64로 인코딩합니다.
echo -n 'internal_backup' | base64
# aW50ZXJuYWxfYmFja3Vw
  1. 존재 확인 API로 이 키가 있는지 확인합니다.
/api/share/check?key=aW50ZXJuYWxfYmFja3Vw
  1. 200 OK가 나오면 아래 공유 링크를 엽니다.
/share/aW50ZXJuYWxfYmFja3Vw
  1. 공유 노트 내용에 flag가 출력됩니다.
최종 정답: FLAG{c7f_2nc0d3d_1D0r_3uCces2}

왜 이렇게 하는가?

서버가 "로그인했는가"만 확인하고 "이 note를 볼 수 있는 사람인가"를 확인하지 않기 때문입니다. 따라서 note_key만 맞히면 다른 사람 또는 내부용 공유 노트도 열 수 있습니다.

5. File Upload

문제 목표테마팩 ZIP 업로드로 내부 승인 파일을 만들고, 게시 과정에서 release token을 출력합니다.
핵심 취약점ZIP 엔트리 검증은 원본 파일명을 기준으로 하고, 실제 저장은 URL 디코딩과 경로 정규화 후 수행합니다.
취약 경로%2e%2e/review/approval.json → ../review/approval.json
승인 파일 내용{"approved": true}

풀이 사고 흐름

처음에는 업로드 후 게시 조건을 봅니다. 테마 ZIP을 올리고 publish를 누르면 release token이 나오는 구조입니다. 따라서 flag가 나오는 조건은 publish 코드에 있을 가능성이 큽니다.

게시 코드에서 내부 승인 파일을 찾습니다. review/approval.json이 있고 그 안의 approved가 true이면 /flag.txt를 읽습니다.

그럼 목표는 review 폴더에 파일을 쓰는 것입니다. 사용자는 원래 source 안에 테마 파일만 올릴 수 있어야 합니다. 하지만 ZIP 내부 파일명 처리에 문제가 있으면 다른 폴더에 쓸 수 있습니다.

검증과 저장의 차이를 봅니다. 검증은 원본 이름에서 ../만 찾지만, 저장 단계는 먼저 URL 디코딩을 합니다. 그래서 %2e%2e가 검증 후에 ..로 바뀝니다.

최종 경로 검사가 root까지만 제한하는 것도 중요합니다. 파일이 theme root 밖으로 나가는지는 막지만, source 밖의 같은 theme root 안에 있는 review 폴더로 가는 것은 막지 못합니다.

개념 이해

ZIP 업로드 문제에서는 압축 안의 파일명이 실제 저장 경로가 됩니다. 안전하게 만들려면 파일명을 디코딩하고 정규화한 뒤, 최종 저장 위치가 의도한 추출 폴더 안인지 확인해야 합니다.

이 문제는 검증할 때는 %2e%2e/review/approval.json을 그대로 보고, 저장할 때는 URL 디코딩해서 ../review/approval.json으로 바꿉니다. 결과적으로 source 폴더에서 한 단계 올라가 review 폴더에 파일을 만들 수 있습니다.

페이로드 ZIP 구조

manifest.json
assets/preview.txt
css/style.css
%2e%2e/review/approval.json

approval.json의 내용은 아래와 같습니다.

{"approved": true}

페이로드 파일 만들기

현재 디렉토리에는 이미 themedock_exploit.zip이 있습니다. 새로 만들려면 아래 명령을 실행합니다.

python3 -c 'import zipfile, json, pathlib; out=pathlib.Path("themedock_exploit.zip"); manifest={"name":"Approved Theme","description":"release metadata test","version":"1.0","entry":"assets/preview.txt"}; css=".theme-surface{padding:24px;color:#18212f;background:#fff}"; preview="approved release test"; z=zipfile.ZipFile(out,"w",zipfile.ZIP_DEFLATED); z.writestr("manifest.json",json.dumps(manifest)); z.writestr("assets/preview.txt",preview); z.writestr("css/style.css",css); z.writestr("%2e%2e/review/approval.json",json.dumps({"approved": True})); z.close(); print(out.resolve())'

Step by Step

  1. 문제 서버의 메인 페이지에서 Theme Pack ZIP 업로드 폼을 엽니다.
  2. themedock_exploit.zip을 업로드합니다.
  3. 서버는 정상 테마 파일인 manifest.json, assets/preview.txt, css/style.css를 처리합니다.
  4. 동시에 %2e%2e/review/approval.json 엔트리가 URL 디코딩되어 review/approval.json 위치에 저장됩니다.
  5. 업로드 결과 페이지에서 preview를 열고 처리가 완료됐는지 확인합니다.
  6. Publish 버튼을 누릅니다.
  7. 게시 페이지에 release token이 출력됩니다.
최종 정답: FLAG{theme_pack_paths_change_after_normalization}

왜 이렇게 하는가?

문제의 flag 출력 조건은 "내부 승인 메타데이터가 있다"입니다. 직접 review 폴더에 접근할 수는 없지만, ZIP 엔트리 이름의 디코딩 타이밍 차이를 이용하면 업로드 과정에서 그 파일을 대신 만들 수 있습니다.

방어 관점에서 기억할 점

  • Command Injection: 사용자 입력을 shell 문자열에 붙이지 말고, subprocess.run(["nslookup", host], shell=False)처럼 인자 배열로 실행해야 합니다.
  • SQL Injection: SQL은 문자열 조합이 아니라 파라미터 바인딩으로 실행해야 합니다.
  • SSTI: 사용자 입력을 템플릿 소스로 다시 렌더링하면 안 되며, 출력 데이터로만 다뤄야 합니다.
  • IDOR: Base64나 난독화는 권한 검사가 아니며, 객체 조회 전 소유권 또는 공유 권한을 확인해야 합니다.
  • File Upload: 파일명은 모든 디코딩과 정규화를 먼저 끝낸 뒤 검증해야 하고, 최종 경로는 반드시 의도된 추출 디렉토리 안으로 제한해야 합니다.
